## Spring Boot backend design for your ERP

You can map the existing Rust core design to a Spring Boot backend cleanly by keeping the same modular domain structure, multi-tenant DB model, and JWT/RBAC approach.

## 1. Overall architecture

Use a Spring Boot application with modular packages or Maven modules:

- `core` / `app` — main Spring Boot service
- `shared` — common config, security, tenant context, error handling
- `auth` — authentication + user profile
- `hrm` — HR domain
- `crm` — CRM domain
- `platform` — optional shared platform services, modules registry, health

This mirrors your current architecture:
- gateway → Spring Boot app
- shared → shared package
- auth/hrm/crm crates → separate packages or submodules

## 3. Database strategy

### Use PostgreSQL + Flyway
- `src/main/resources/db/migration/V1__init.sql`
- port your existing SQL schema into Flyway migration scripts
- keep the existing tables:
  - `tenants`
  - `users`
  - `hr_locations`
  - `hr_departments`
  - `hr_positions`
  - `hr_employees`
  - `hr_leave_requests`
  - `hr_requisitions`

### Multi-tenancy
Keep the same RLS model:
- PostgreSQL `app.current_tenant`
- policy on tenant-scoped tables
- `diigoo_app` DB role

In Spring Boot, set the tenant before each request:
- `OncePerRequestFilter` reads tenant from JWT
- set `CURRENT_SETTING('app.current_tenant')` on every DB connection
- use a connection proxy or `DataSource` wrapper

Example flow:
1. Request arrives
2. JWT validated
3. Tenant id extracted
4. `TenantContext.setCurrentTenant(tenantId)`
5. SQL connection executes:
   ```
   SELECT set_config('app.current_tenant', ?, false)
   ```
6. RLS applies automatically

## 4. Security design

### JWT authentication
- `/api/v1/auth/login`
- `/api/v1/auth/me`

JWT claims:
- `sub` = user id
- `tid` = tenant id
- `role`
- `eid` = employee id
- `iss` = issuer

### Spring Security
- `JwtAuthenticationFilter`
- `JwtTokenProvider`
- `UserDetailsService` loads from `users`
- `PasswordEncoder` = `BCryptPasswordEncoder`

### RBAC
Implement a service like:
- `AuthorizationService.can(role, action, module)`

Define:
- `Action { CREATE, READ, UPDATE, DELETE, APPROVE, OPERATE, EXPORT }`
- `Module { HR, SALES_CRM, FINANCE, AI_ANALYTICS, SYSTEM_ADMIN, INTEGRATIONS }`

Use either:
- explicit service checks inside controllers/services
- or `@PreAuthorize` with custom role evaluator

Example:
- HR analytics: require `READ` on `HR`
- employee creation: require `CREATE` on `HR`
- leave approval: require special roles like `HR_MANAGER`, `OWNER`, `ACCOUNTANT`
